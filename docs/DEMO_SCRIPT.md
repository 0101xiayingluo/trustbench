# TrustBench 三分钟 Demo 脚本

目标：在 3 分钟内证明这是一个可运行的 AI Agent 评测与治理产品，而不是审批页面或静态 Mock。

## 0:00-0:25 问题与产品定位

画面：打开 `http://127.0.0.1:5173/showcase/`，停留在首屏和产品截图。

口播：

> TrustBench 面向增长活动等复杂业务流程。它不只判断 Agent 最终有没有完成任务，还评测执行路径是否安全、业务规则是否满足，以及 Token、成本和延迟是否达到发布门槛。

## 0:25-0:55 风险路由

画面：滚动到“风险路由 Demo”。依次点击“只读巡检”“审批上线”“低 ROI 攻击”，每次点击“运行评测”。

口播：

> 我把 Agent 动作按只读、可撤销和高风险不可逆分为三级，再用预算、ROI、权限、可逆性和时段五类信号计算风险分。低于 40 自动通过，40 到 70 人工确认，高于 70 在模型调用和浏览器执行前拦截。这里的规则由产品定义，不依赖模型自己判断风险。

## 0:55-1:25 双基线与阈值迭代

画面：停留在“基线实验”和“阈值调优”。

口播：

> 为避免只报拦截率，我设计了两组对照。相对无前置治理基线，六条危险路径的放行率从 100% 降到 0%；相对全人工确认基线，人工确认从十次降到四次，下降 60%。误拦截率和无效确认率均为 0%，但只代表封闭验证集。初版 50/80 阈值曾有三条边界误路由，经过 12 条校准样本调整为 40/70 后才归零。

## 1:25-1:50 策略权衡与商业价值

画面：展示三档 Pareto 表格、模型降级规则；在 ROI 情景计算器中修改一次“预计防控率”。

口播：

> 阈值不是越严越好。自动化优先少干预，但漏掉一条危险样本；安全优先多干预且产生误拦截，却没有提升危险召回，因此当前选择 40/70。模型超时、计划无效和价格缺失也都有 fail-closed 降级路径。这里的 ROI 是可调整情景模型，明确不代表实际上线收益。

## 1:50-2:25 真实执行证据

画面：点击“打开评测控制台”，进入任务中心运行一条静态基准任务；随后进入“运行详情”，依次展示运行概览、轨迹回放和运行对比。

口播：

> Runner 只接受 click、fill、press 和 waitFor 四类声明式动作。每一步都保存状态快照，评测器从结果、安全、效率和业务规则四个维度出报告，并把失败归因到规划、状态漂移、安全策略、业务规则或执行异常。相同协议也可以接入真实 OpenAI Agent。

## 2:25-2:45 发布决策与运营指标

画面：进入“发布决策”，展示 GO/NO-GO 门禁和 Token、成本、延迟字段。

口播：

> 真实模型运行会记录输入、缓存、输出和推理 Token、API 延迟及估算成本。缺失模型定价时系统返回数据不足，而不是把成本显示为零。最终由通过率、安全、成本、延迟和定价覆盖共同决定能否发布。

## 2:45-3:00 验证结论

画面：返回作品集的“交付证据”。

口播：

> 当前封闭验证集包含十条正向流程和六条攻击路径，连续三轮共 48 次执行全部通过，波动用例为零；同时完成 56 项单元测试和 5 项 E2E。它验证的是本地可复现的治理闭环，不把样例指标包装成生产效果。

## 录制检查

- 浏览器使用 1440 × 900 或 1920 × 1080，缩放 100%。
- 录制前先运行 `npm.cmd run test:stability`，确保页面数据与报告一致。
- 若演示真实模型，提前配置测试 API Key，并明确标注模型、日期和单次运行；没有 Key 时使用静态计划，禁止声称是真实模型调用。
- 不展示 `.env`、Authorization 请求头或本机绝对路径。
