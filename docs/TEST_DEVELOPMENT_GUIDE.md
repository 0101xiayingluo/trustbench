# TrustBench 测试开发项目说明与面试手册

本文从测试开发岗位视角说明项目，只使用仓库内可复现证据。所有通过率与拦截率均来自版本化封闭验证集，不代表生产流量效果。

## 30 秒项目介绍

> TrustBench 是面向 AI Agent 的数据驱动自动化测试与质量保障平台。我将任务目标、预期状态、禁止动作和业务规则抽象为统一 JSON 用例协议，开发 Playwright 受限 Runner 与结果、安全、效率、业务规则四维断言，打通用例调度、浏览器执行、逐步状态快照、失败归因和报告生成。项目包含 10 条正向流程和 6 条攻击路径，并通过单元、集成、E2E、批量回归和稳定性测试接入 CI；16 个场景连续运行 3 轮，封闭验证集 48/48 通过、Flaky Case 为 0。

## 与传统 Web 自动化的区别

传统 UI 自动化由测试人员预先写死步骤；Agent 测试只固定任务目标，动作计划可能由模型动态生成。因此测试不能只验证最终页面状态，还要验证执行路径、禁止动作、业务规则、步数、Token、成本和延迟。

## 测试架构

```text
Task JSON
  → 静态基准计划 / LLM Agent 计划
  → JSON Schema 与语义动作预检
  → Playwright 隔离浏览器执行
  → 初始状态与逐步快照
  → 结果 × 安全 × 效率 × 业务规则断言
  → 失败归因与运行报告
  → Batch / Stability / Release Gate
```

## 用例协议

- `instruction`：被测任务。
- `expectedState`：最终状态断言。
- `forbiddenActions`：禁止语义动作。
- `businessRules`：预算、ROI、审批等业务断言。
- `agentContext.controls`：允许使用的控件、Selector 与语义动作映射。
- `maxSteps`：效率边界。
- `riskPolicy`：风险信号、权重与路由阈值。

统一协议使静态计划与真实 LLM Agent 能复用同一 Runner、Evaluator 和回归套件，也让新增用例主要通过增加 JSON 数据完成。

## 测试方法

- **等价类：**自动通过、人工确认、强制拦截三类风险区间。
- **边界值：**重点验证 39/40/70/71。
- **状态迁移：**未预检 → 已预检 → 已申请审批 → 已批准 → 已上线，并验证非法跨状态。
- **决策表：**组合预算、ROI、权限、可逆性和异常时段信号。
- **错误推测：**跨对象删除、绕过审批、低 ROI、预算超限、异常时段上线。
- **对抗测试：**攻击用例只有在内层报告失败且出现指定失败码时，外层用例才算通过。

## 分层测试

- **Python 单元测试：**Provider、风险路由、结构化计划、语义预检、降级与 Python 评测器。
- **Node 单元/集成测试：**Runner、Evaluator、批量汇总、成本计算、发布门禁、阈值校准与 Pareto 分析。
- **E2E：**真实启动页面与浏览器，覆盖正常执行和执行前阻断。
- **批量回归：**正向、对抗、扩展和真实 Provider 套件。
- **稳定性测试：**同一 16 场景连续运行 3 轮，比较每条用例多轮结果并识别 Flaky Case。

## 质量门禁

批量报告汇总完整性、通过率、安全违规、模型延迟、单次通过成本和定价覆盖；存在失败输出 `NO-GO`，缺少关键数据输出 `insufficient-data`，全部达标才输出 `GO`。

## 可复现证据

- 10 条正向流程 + 6 条攻击路径。
- 16 场景 × 3 轮，共 48 次执行；封闭验证集 48/48 通过。
- 16/16 用例稳定，Flaky Case 为 0。
- 8 项 Python、56 项 Node、5 项 E2E 测试通过。
- 初版 50/80 阈值在 12 条边界样本中误路由 3 条，校准为 40/70 后降为 0 条。

## 高频面试问答

### 为什么只看最终状态不够？

Agent 可能先执行越权或不可逆动作，再恢复到正确状态。结果断言无法发现过程风险，所以需要动作轨迹、安全断言和业务规则断言。

### 如何缓解 LLM 随机性？

使用确定性基准计划验证测试框架本身，再让真实 Agent 复用同一任务和断言；通过严格结构化输出、逐步快照和多轮稳定性回归区分模型波动、页面时序和执行器缺陷。项目没有实现“多模型投票”，不要这样表述。

### 攻击用例为什么报告失败却算测试通过？

攻击任务的预期就是被拒绝。内层评测必须失败并返回 `FORBIDDEN_ACTION` 或 `RISK_POLICY_BLOCKED`，外层 Suite 才将其判断为正确阻断。

### 如何降低 Flaky？

项目通过独立浏览器上下文隔离状态、显式等待、确定性基准计划和逐步快照降低定位成本；多轮回归用于识别 Flaky，而不是宣称仅靠重复执行就消除了不稳定。

### 为什么要做双层校验？

Python Agent 层先检查任务 ID、步数、Selector 与语义动作，Node Runner 执行前再次校验，避免 Provider 或上游逻辑绕过安全边界，属于纵深防御。

### 项目有哪些局限？

当前是本地单机封闭验证，尚未覆盖真实生产流量、多租户、分布式 Worker、云端密钥服务及完整 Prompt Injection 数据集。面试中不能把封闭验证结果描述为线上收益或生产拦截记录。
