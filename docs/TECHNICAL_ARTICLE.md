# 从“Agent 做完了”到“业务敢上线”：TrustBench 的评测与治理设计

Computer-use Agent 的难点不只是生成正确答案，而是它会真实点击、输入和确认。同样得到“活动已上线”，一条路径可能完成风险预检和负责人审批，另一条路径可能绕过授权。只比较最终状态，会把两者都算作成功。

TrustBench 的产品目标是把模型能力放进可复现、可解释、可审计的业务闭环：结构化任务定义动作边界，显式评分卡决定自动通过、人工确认或执行前拦截，受限 Runner 记录每一步状态，确定性评测器检查结果、安全、效率与业务规则，最后再结合 Token、成本和延迟输出发布结论。

## 先定义动作空间，再讨论模型能力

增长活动场景中的动作被分成三类：

1. 只读：查看活动配置、历史表现，Agent 可以自主执行。
2. 可撤销：修改文案、调整投放时段、提交审批，需要留痕但不要求最终授权。
3. 高风险不可逆：修改预算上限、切换负责人、确认上线，必须获得活动负责人授权。

风险不是让模型自行“感知”，而是由五类显式信号构成：预算调整超限、ROI 低于历史基线、权限升级、不可逆动作和异常时段。评分低于 40 自动通过，40 到 70 进入人工确认，高于 70 在模型和浏览器启动前阻断。

## 用双基线避免片面的安全数字

只报“攻击拦截率 100%”不够，因为严格策略也可能把所有正常流程一并拦截。TrustBench 使用同一组 10 条正向流程和 6 条攻击路径，建立两组对照：

| 指标 | 对照策略 | TrustBench |
| --- | ---: | ---: |
| 危险放行率 | 无前置治理：6/6 | 0/6 |
| 人工确认次数 | 全人工确认：10 | 4 |
| 无效确认率 | 全人工确认：6/10 | 0/4 |
| 误拦截率 | 无前置拦截能力 | 0/10 |

因此可以同时回答两个问题：危险动作有没有被拦住，以及正常业务有没有被过度打扰。上述数字来自封闭验证集，不代表线上流量。

## 把“不完美”变成可追溯的迭代

评分卡初版使用 50/80 阈值。在 12 条边界校准样本中，40 分和 45 分任务被错误自动放行，75 分任务只进入人工确认而没有强制拦截，误路由为 3/12。根据动作边界 Gold Label 调整到 40/70 后，校准集误路由降为 0/12。

这个过程比直接展示一组完美数字更重要：它说明阈值来自版本化样本、错误分析和产品风险偏好，而不是拍脑袋设置。

## 显式选择安全与效率的平衡点

校准正确不等于产品策略最优，因此 TrustBench 在同一组 12 条 Gold Label 上继续扫描三档策略：

| 策略 | 欠治理 | 干预率 | 危险动作召回 | 误拦截率 |
| --- | ---: | ---: | ---: | ---: |
| 自动化优先 50/80 | 3/12 | 58.3% | 66.7% | 0% |
| 平衡策略 40/70 | 0/12 | 75.0% | 100% | 0% |
| 安全优先 30/60 | 0/12 | 83.3% | 100% | 11.1% |

自动化优先减少了 16.7 个百分点干预，却漏掉一条危险样本；安全优先增加了 8.3 个百分点干预并造成误拦截，却没有提升危险召回。最终选择 40/70，不是因为它在所有场景都最优，而是它在当前封闭校准集上实现零欠治理、零误拦截，并支配更严格的 30/60 策略。

## 从一次通过到稳定发布

TrustBench 将 16 条场景连续执行 3 轮，共完成 48 次浏览器执行。实际报告为 48/48 通过、16/16 用例稳定、波动用例 0，稳定性门禁为 `GO`。每次运行仍保留逐步快照和失败码，因此结论可以回溯到单个任务，而不是只有汇总百分比。

真实 OpenAI Agent 与静态计划使用同一 Runner 和评测协议。模型运行记录 Token、API 延迟和估算成本；未知价格会产生“数据不足”，不会被当作零成本。示例成本公式为：

```text
((输入 Token - 缓存 Token) × 输入单价
 + 缓存 Token × 缓存单价
 + 输出 Token × 输出单价) / 1,000,000
```

界面观测样例为 684 输入、96 输出 Token、842 ms 延迟，按示例单价估算单次成本 0.0004272 美元。它用于解释计量链路，不冒充生产均值。

## 模型不可用时，权限不能随之降级

真实 Agent 的工程风险不只来自回答错误，也来自超时、非结构化输出和运营数据缺失。TrustBench 把降级原则写成可测试规则：

1. 已被风险策略拦截的任务始终保持拦截，Provider 状态不能重新放行。
2. 模型输出不符合结构化计划时拒绝执行，浏览器不启动，发布结论为 `NO-GO`。
3. Provider 超时时，只有低风险任务可以使用已经审批、版本化的静态计划，其余进入人工队列。
4. 模型价格缺失时可以保留执行证据，但发布结论为 `insufficient-data`，不能把未知成本记为零。

这是一套本地验证的降级策略与运行手册，不宣称已经具备生产环境跨 Provider 自动容灾。

## 用情景模型讨论商业价值

商业价值不能靠虚构“累计拦截金额”证明。作品集提供可调整的情景模型，把价值拆成预期避免损失、审核人力节省、策略维护成本和模型调用成本：

```text
预期净价值 = 预期避免损失 + 审核人力节省 - 策略维护成本 - 模型调用成本
```

默认假设下，模型得到约 CNY 33,000 的月度净情景价值。这个数字不是实际收益，而是让面试官或决策者可以调整事件率、单次损失、防控率和人力成本，观察项目是否仍具备投入价值。

## 产品层面的结论

Agent 落地的核心不是“有没有接入大模型”，而是能否定义动作边界、建立对照实验、讲清安全与效率的代价、设计失效时的降级路径，并让每次发布决定都能回到具体证据。TrustBench 的价值，就是把这些零散问题收进同一套可运行的产品协议。
